# VALORANT: собственный детектор без Overwolf и Riot API

Дата проверки: 19 октября 2026. Это исследование первичных источников и архитектурных ограничений. Никакие запросы к Riot API, чтение памяти игры, захват экрана или проверки в живом матче в рамках этой заметки не выполнялись. Изменений приложения нет.

## Вывод

Реалистичный вариант для этого проекта — собственное Electron-приложение, в котором Node читает существующий лог игры, а распознавание изображения служит необязательным дополнительным источником. Это собственное устанавливаемое приложение: Electron не устраняет загрузку приложения пользователем, но позволяет обойтись без Overwolf, отдельного BAT/PowerShell helper и дополнительных программ. Возможности Node в главном процессе описаны в [Electron Process Model](https://www.electronjs.org/docs/latest/tutorial/process-model), чтение и наблюдение файлов — в [Node fs](https://nodejs.org/api/fs.html).

Для обычного сайта без установки остаётся захват выбранного пользователем окна/экрана и собственное распознавание. Полностью незаметное подключение страницы к состоянию другой Windows-программы из этих браузерных механизмов не получается: capture требует выбора источника и повторного согласия при новом вызове; файловый доступ ограничен выбранными пользователем путями. [Screen Capture specification](https://w3c.github.io/mediacapture-screen-share/), [File System Access specification](https://wicg.github.io/file-system-access/).

## Браузер: захват окна и распознавание

`getDisplayMedia()` возвращает поток изображения выбранного пользователем экрана, окна или вкладки. Полученные кадры можно использовать как вход собственного классификатора экранов/OCR; наличие capture API само по себе не даёт событий VALORANT и не доказывает точность классификатора. Для нового вызова нужен жест пользователя; разрешение `granted` сохранять нельзя, выбор источника повторяется. Продолжение уже открытого потока не требует повторного выбора на каждом кадре. [W3C Screen Capture](https://w3c.github.io/mediacapture-screen-share/).

Нельзя обещать работу на свёрнутой игре. Спецификация допускает недоступность поверхности при минимизации; при временной недоступности track переводится в `muted`. Видимость перекрытого окна зависит от реализации: скрытые области могут замораживаться или заменяться заглушкой. Для capture всего монитора экран другой программы после Alt+Tab сам по себе не показывает игру. Fullscreen, borderless, Alt+Tab и сворачивание нужно проверять на конкретных Windows/видеодрайвере/браузере. Это ограничение источника изображения, а не только качества OCR. [W3C: Closed and Minimized Display Surfaces; Capturing Logical or Visible Display Surfaces](https://w3c.github.io/mediacapture-screen-share/).

Практический UX-прототип: «Подключить окно игры» → пользователь выбирает окно → локально различаем меню/очередь/выбор агента/матч → явно показываем «Источник недоступен», когда изображение потеряно. Не считать отсутствие кадра доказательством выхода из очереди или закрытия игры. Это проектное предложение, не проверенная реализация.

## Браузер: чтение логов — важная поправка к прежнему исследованию

File System Access действительно умеет читать пользовательский файл через handle и `getFile()`. При внешнем изменении файла необходимо получать новый `File`; старый объект не является бесконечным живым хвостом. Picker требует secure context и пользовательского действия. [Chrome File System Access guide](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access).

Chrome с версии 122 предлагает сохраняемые разрешения на файлы/папки. Это отдельная возможность файлового доступа; её нельзя переносить на разрешение screen capture. Сохраняемость также не отменяет ограничения доступных путей. [Chrome persistent file permissions](https://developer.chrome.com/blog/persistent-permissions-for-the-file-system-access-api).

**Блокирующее ограничение стандартного расположения лога:** в текущем исходном коде Chromium Windows-путь `base::DIR_LOCAL_APP_DATA` помечен `BlockType::kBlockAllChildren`; такие же ограничения есть для roaming/common AppData. `ShouldBlockAccessToPath()` разрешает read-only исключение только для правил `kBlockWrite`, а отдельные файлы — для `kBlockNestedDirectories`. Эти исключения к LocalAppData не относятся. Следовательно, стандартный `%LOCALAPPDATA%\VALORANT\Saved\Logs\ShooterGame.log` попадает под блокировку прямого File System Access, даже если нужен только read-only доступ. Это вывод по текущему upstream-коду, не воспроизведение picker в установленной версии браузера пользователя. [Chromium permission context, Windows blocklist и ShouldBlockAccessToPath](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/file_system_access/chrome_file_system_access_permission_context.cc).

Поэтому прежний совет «выбрать лог непосредственно в браузере» нельзя считать готовым основным решением. Ручная копия файла в другую папку не становится автоматически обновляемым источником исходного лога. Обходы через флаги, перенос системных папок или отдельный copier противоречат желаемому простому UX и здесь не предлагаются.

Наблюдение файлов уже не ограничено polling: официальный ChromeStatus сейчас указывает `FileSystemObserver` как **Enabled by default**, desktop milestone **133**. Данные карточки получены также напрямую из её официального JSON endpoint; старая статья об origin trial не отражает весь нынешний статус. Нужна проверка наличия API в выбранном браузере. [ChromeStatus](https://chromestatus.com/feature/4622243656630272), [официальные данные карточки](https://chromestatus.com/api/v0/features/4622243656630272).

Observer работает только с уже разрешёнными handles, не расширяет доступ и не гарантирует доставки каждого изменения. Он не решает AppData blocklist. Обработчик обязан уметь перечитывать состояние после `unknown`/ошибки и пересоздавать наблюдение после новой сессии. [WHATWG FileSystemObserver explainer: Non-Goals; Handling Changes Outside Lifetime](https://github.com/whatwg/fs/blob/main/proposals/FileSystemObserver.md).

При fallback на таймеры фоновые вкладки подвержены ограничению частоты; нельзя обещать фиксированную задержку детекта. [Chrome timer throttling](https://developer.chrome.com/blog/timer-throttling-in-chrome-88).

## Electron: собственное приложение без стороннего провайдера событий

Главный процесс Electron имеет Node-окружение. Чтение лога следует держать там; renderer получает только минимальное очищенное состояние через ограниченный preload/IPC. Открывать Node произвольному удалённому контенту не требуется. [Electron Process Model](https://www.electronjs.org/docs/latest/tutorial/process-model), [Electron security checklist](https://www.electronjs.org/docs/latest/tutorial/security).

`fs.watch` на Windows использует `ReadDirectoryChangesW`; он сигнализирует об изменениях файлов, а не о найденном матче. Документация предупреждает о различиях платформ, пропусках при переносе наблюдаемой директории и `EPERM` при её удалении. Предлагаемая реализация: наблюдать узкую папку, дочитывать новые байты последовательно, обрабатывать truncate/rotation, переоткрытие файла и ошибки watcher, периодически сверять текущее содержимое/размер. Надёжность переходов определяется и реальным содержимым лога, а не только способом наблюдения. [Node fs.watch caveats](https://nodejs.org/api/fs.html#fswatchfilename-options-listener).

Electron также предоставляет `desktopCapturer.getSources({types:['window','screen']})`; выбор источника можно обслуживать через `session.setDisplayMediaRequestHandler` в собственном приложении. Это устраняет необходимость отдельно устанавливать провайдера capture, но не превращает кадры в готовые игровые события и не гарантирует захват минимизированного VALORANT. Возможность автоматического выбора окна в собственном приложении отличается от ограничений обычного сайта. [Electron desktopCapturer](https://www.electronjs.org/docs/latest/api/desktop-capturer), [Electron session display media handler](https://www.electronjs.org/docs/latest/api/session#sessetdisplaymediarequesthandlerhandler-opts).

Предлагаемый порядок источников: локальный лог → при недостаточном покрытии добровольно включаемый capture → ручное переключение. Не добавлять чтение памяти, инъекции, hooks или скрытые Riot Client endpoints под видом «без Riot API».

## Что подтверждено существующим локальным логом

При чтении существующего файла обнаружены следующие записи в сохранённом логе с датой последнего изменения 18 октября, около 24 МБ:

| Переход | Найдено |
| --- | ---: |
| MainMenu → TransitionToPregame | 8 |
| TransitionToPregame → Pregame | 8 |
| Pregame → TransitionToInGame | 6 |
| TransitionToInGame → InGame | 10 |
| InGame → TransitionToMainMenu | 7 |
| Pregame → TransitionToMainMenu | 2 |

Источник: существующий локальный `ShooterGame.log`, прочитанный в текущем исследовании. Сам файл и сетевые идентификаторы не добавлялись в репозиторий. Также встречаются replay-переходы: нельзя объединять их с собственным активным матчем.

Имеются исторические сообщения об ответах на matchmaking join/leave: join 200 — 5, join 403 — 1, leave 200 — 2. Их пассивное чтение не означает выполнение API-запросов приложением. Строка успешного join означает завершение операции постановки в очередь, а не самостоятельное доказательство `match found`. Наличие 8 входов в pregame при 5 успешных join уже не позволяет выдавать этот snapshot за полную телеметрию всех сессий и режимов. Точное `MatchFound` встречалось как ссылка на audio asset, поэтому его нельзя использовать как подтверждённое событие. Это анализ ограниченного существующего файла; нет измерений задержки, полноты событий или ложных переходов в живой игре.

## Текущий BAT-путь в проекте

Проверены актуальные исходники: `components/hud/SyncHelpDialog.tsx` предлагает `/api/install-sync-ps`; `app/api/install-sync-ps/route.ts` генерирует BAT, скачивающий `public/companion.ps1`, и создаёт VBS launcher для автозапуска PowerShell. Этот PowerShell читает лог и обслуживает localhost-порт 23115. Он не выполняет запросов к Riot API, но отдельного статуса очереди или события match found в его контракте нет: только `offline`, `lobby`, `pregame`, `match`.

`public/companion.ps1` считает отсутствие записи в течение 45 секунд признаком закрытой игры без проверки процесса. Он возвращает карту только для `match`, не возвращает `timestamp`; в `components/hud/LiveSyncStatus.tsx` автоматическая навигация требует `timestamp`. Поэтому проблемы текущего UX нельзя сводить к формату установщика: parser и контракт тоже требуют переработки.

Альтернативные `scripts/companion.js` и `app/api/detect-map/route.ts` содержат обращения к внутренним Riot pregame/core-game endpoint. Для этого запроса их нельзя предлагать как вариант «без Riot API». Ни helper, ни эти route в рамках исследования не запускались.

## Политика Riot: отдельный вопрос от технической возможности

VALORANT Developer Portal требует регистрации player-facing продукта даже без официальных документированных API. Там также ограничены unfair advantage и real-time подсказки, сразу изменяющие поведение игрока; запрещён scouting скрытых/не согласившихся игроков. Страница не содержит отдельного явно сформулированного одобрения автоматического agent-select picker или OCR. Поэтому «без API» не означает «автоматически разрешено». Вывод: конкретный UX определения собственной фазы игры и автоматического открытия справочника нельзя уверенно объявлять ни одобренным, ни тождественным запрещённой live-подсказке. [Riot VALORANT policies](https://developer.riotgames.com/docs/valorant).

Свежая официальная публикация Riot от 29 сентября 2026 сообщает о блокировке доступа неизвестных сторонних приложений к памяти игр начиная с 6 октября 2026 и переходном периоде для известных одобренных инструментов до апреля 2027. Это ещё одна причина исключить memory scraping из предложений. Публикация не является явным одобрением нашего log/OCR решения и не даёт гарантии отсутствия санкций за любые сторонние функции. [Riot: Game Memory Access Removed for Third Party Apps](https://support.riotgames.com/en-us/riot/performance/game-memory-access-removed-for-third-party-apps).

## Следующая проверка перед реализацией

Проверить сценарии новой и отменённой очереди, match found, dodge, выбор агента, loading, матч, replay, выход, reconnect и повторный матч. Отдельно измерить, какие переходы и поля доступны до начала матча, и задержку относительно видимого экрана. Для захвата дополнительно проверить fullscreen/borderless, Alt+Tab, перекрытие, минимизацию, разные разрешения и язык. Процент точности и допустимость по Riot сейчас не установлены.
