# Детект Valorant: варианты подключения и надёжность

Дата проверки: 13 октября 2026 года. Проект: Agent Academy / `valorant-picker`.

## Решение, которое я рекомендую

Оставить сайт полностью полезным без подключения к игре: быстрый ручной выбор карты и агента, сохранение выбора и избранных заготовок. Автодетект сделать дополнительной возможностью.

Если приоритет — **ничего не устанавливать**, следующий исследовательский шаг — небольшой браузерный прототип чтения выбранного пользователем лога через File System Access API. Это технически обоснованная гипотеза, а не уже проверенное подключение к Valorant. Она убирает `.bat`, PowerShell, автозапуск и localhost, но не гарантирует точный статус процесса, карту на выборе агента или постоянную работу в фоне.

Если приоритет — **полный автоматический детект**, сначала проверить Overwolf Electron + Game Events Provider (GEP), а затем сравнить с собственным подписанным Windows helper. Overwolf Electron позволяет выпускать самостоятельное приложение без отдельного клиента Overwolf; скачивание нашей программы остаётся. Доступность нужных событий и конкретной игры для приложения нужно подтвердить у Overwolf. [Frameworks overview](https://dev.overwolf.com/ow-electron/getting-started/onboarding-resources/frameworks-overview/), [GEP](https://dev.overwolf.com/ow-electron/live-game-data-gep/live-game-data-gep-intro/).

Официальный Riot API + Riot Sign On полезен для **истории сыгранных матчей** и статистики без локальной установки. В опубликованном каталоге нет endpoint для процесса на ПК, текущего pregame/core-game или live party игрока. Это вывод из опубликованного интерфейса, а не утверждение об отсутствии любых закрытых партнёрских возможностей. [Riot VALORANT docs](https://developer.riotgames.com/docs/valorant), [API catalog](https://developer.riotgames.com/apis).

## Что именно нужно различать

- **Запущен процесс:** игра действительно работает на конкретном компьютере.
- **Состояние клиента:** меню, очередь, выбор агента, загрузка, матч, завершение.
- **Контекст матча:** стабильный match ID, карта, собственный агент; при необходимости сторона и раунд.
- **История:** сыгранные матчи, результаты и агрегаты после появления данных в API.

Старый лог, вход в Riot Account и наличие Riot Client сами по себе не доказывают, что Valorant сейчас запущен. История матчей не заменяет моментальный детект выбора агента.

## Как устроен проект сейчас

Предлагаемый пользователю путь:

1. `components/hud/SyncHelpDialog.tsx:44` скачивает `/api/install-sync-ps`.
2. `app/api/install-sync-ps/route.ts:25` генерирует `.bat`, который скачивает **`public/companion.ps1`** с текущего origin.
3. Installer сохраняет скрипт в `%USERPROFILE%\VALORANT-Sync`, создаёт скрытый VBS launcher в Windows Startup и запускает PowerShell с `ExecutionPolicy Bypass`.
4. `public/companion.ps1:75` читает `%LOCALAPPDATA%\VALORANT\Saved\Logs\ShooterGame.log`.
5. Helper слушает `http://127.0.0.1:23115/detect-map`; `LiveSyncStatus.tsx:50` опрашивает его, а затем при ошибке пробует серверный `/api/detect-map`.

В репозитории есть также более сложный **`scripts/companion.js`**: он читает Riot Client lockfile, получает локальные токены, обращается к внутренним pregame/core-game endpoint и при исключении использует лог. Аналогичная логика находится в Next.js route. Однако текущая кнопка установки предлагает PowerShell, а не эту JS-версию. Исходники `public/companion.ps1` и `scripts/companion.ps1` сейчас совпадают по SHA256.

Поэтому утверждение «у нас уже есть API-детект» относится к другой реализации, а не к helper, который устанавливается из текущего интерфейса. Названия комментариев `Secure Riot API` не делают внутренние client endpoint официальным публичным API.

## Подтверждённые проблемы в коде

### 1. Главный дефект: ответ helper не соответствует клиенту

`public/companion.ps1:108` возвращает карту, агента, status и возраст записи, **но не `timestamp`**. В `LiveSyncStatus.tsx:87` автопереход выполняется только при наличии `next.timestamp`.

Следствие: helper может успешно вернуть `match` и `ascent`, сайт покажет состояние, но автоматический переход в этой ветке не выполнится. Ручной клик по индикатору имеет другую логику и может работать. Это конкретный дефект контракта, не предположение о Windows или Riot.

### 2. Тишина в логе ошибочно означает закрытую игру

`public/companion.ps1:81`: если файл не менялся 45 секунд, возвращается `offline` / `VALORANT not running`. Проверки процесса нет. Такой же порог присутствует в log fallback JS-helper и Next route.

Это эвристика возраста данных, а не проверка процесса. Нельзя исправить её только увеличением порога: тогда дольше будет сохраняться ложный online после закрытия игры. Нужны независимые состояния game running и data stale.

### 3. На выборе агента карта отсутствует

PowerShell распознаёт `CharacterSelectPersistentLevel` как `pregame`, но намеренно возвращает `activeMapSlug = null`. Из этой реализации текущую карту на этапе выбора агента получить нельзя. JS-версия делает отдельный pregame запрос, но не используется текущим installer.

### 4. Уже отсутствует нужный alias карты

В `lib/generated/valorant-maps.ts:1561` есть **Corrode** с `mapUrl = /Game/Maps/Rook/Rook`. Во всех трёх detector mapping отсутствует `rook → corrode`. Detector возвращает `rook`, который не совпадает с ключом карты `corrode` в каталоге. Определение «неизвестное имя → матч» также позволяет ошибочно строить URL для служебных уровней и неподдерживаемых карт.

### 5. Старый агент может попасть в новый матч

PowerShell ищет последнее `Pregame_LockCharacter` в хвосте лога без привязки к новой игровой сессии или match ID. JS log fallback тоже ищет последнее событие отдельно от события загрузки карты. Старая запись может быть присоединена к новой карте. Для deathmatch, training, reconnect и пропущенного lock event нужна отдельная логика.

### 6. Нужное событие может выпасть из хвоста

PowerShell каждый раз читает только последние 512 KiB. Если после загрузки карты записалось больше данных, событие `LogMapLoadModel` исчезнет из окна, и helper вернёт `offline` / `No map events`. Нужен parser с сохранением последнего подтверждённого состояния, offset и обработкой перезапуска/ротации файла.

### 7. Серверный fallback не подключает облако к ПК игрока

`app/api/detect-map/route.ts:387` использует `process.env.LOCALAPPDATA` и файловую систему **того компьютера, где выполняется Next.js**. При локальном запуске на игровом ПК это может работать. При удалённом hosting route не получает доступа к пользовательскому ПК. Нельзя считать эту ветку рабочим backup для production localhost-соединения; в текущем коде отсутствие `LOCALAPPDATA` даёт offline.

### 8. Ошибки подключения скрываются под одним Offline

Клиент ловит любые ошибки localhost и пробует сервер; финальный catch снова делает `offline`. Отсутствующий helper, отказ browser permission, несовместимая версия, timeout и закрытая игра не различаются. HTTPS / `isSecureContext` не доказывает, что local network permission выдано.

Chrome ввёл Local Network Access permission начиная с 142. Старый ответный заголовок `Access-Control-Allow-Private-Network: true` не заменяет разрешение пользователя; LNA заменяет прежний эксперимент PNA. Значит, «твики браузера» нужно заменить нормальным подключением и диагностикой. [Chrome LNA](https://developer.chrome.com/blog/local-network-access).

### 9. Дополнительные дефекты JS / API-ветки

- `httpsRequest` не задаёт deadline; зависший запрос задерживает fallback. Browser timeout 1800 ms обрывает ожидание клиента, но не отменяет автоматически все исходящие запросы helper.
- Несколько non-200 ответов pregame/core-game заканчиваются `lobby`; ошибка авторизации, 429 и серверный сбой не различаются с реальным отсутствием матча.
- Region `eu`, cluster `eu-1`, client version и User-Agent имеют жёсткие fallback значения. Ошибка определения может выглядеть как lobby или offline.
- Отдельные реализации дублируют mappings и контракт. Это уже привело к различиям.
- Все origin разрешены через CORS `*`; локальный status endpoint не имеет pairing. Для нового helper нужен allowlist origin и привязка к сайту, без передачи Riot credentials в браузер.
- Installer останавливает любой процесс, занявший порт 23115, не проверяя принадлежность нашему helper. Проверка после установки подтверждает только listening port, не версию сервиса, работу detector или доступ сайта.

## Проверка проблем без запуска и изменения игры

В отдельном PowerShell-процессе исполнены только определения функций из первых 115 строк `public/companion.ps1`. Файловые операции подменены синтетическими входами; HTTP listener, installer и Riot API не запускались.

Получены результаты:

```text
fresh_match            → match, map=ascent, timestamp отсутствует
no_writes_60s          → offline, "VALORANT not running"
agent_select           → pregame, map=null, timestamp отсутствует
corrode (Map Name:Rook)→ match, map=rook
old_agent_then_new_map → match, map=ascent, agent=jett из старой записи
```

Это подтверждает поведение parser и mismatch контракта на указанных входах. Это **не** проверка того, какие строки пишет текущая установленная версия Valorant, и **не** end-to-end тест на реальном матче. Отказы браузерного разрешения и длительные фоновые сессии в этом исследовании не воспроизводились.

## Реальные варианты без скачивания

### Ручной выбор — готовая надёжная основа

Для библиотеки заготовок он решает основную задачу независимо от Riot, браузерных разрешений и фонового helper. Предложение: сохранять карту/агента, дать компактное переключение, недавние карты и быстрый доступ к избранному. Это продуктовая рекомендация, не необходимость интегрировать новый сервис.

### Выбор лога в браузере — перспективный, но ограниченный эксперимент

Пользователь нажимает «Подключить через лог» и выбирает `ShooterGame.log` либо узкую папку `VALORANT\Saved\Logs`. Приложение получает read-only handle и читает изменения локально. Никакой PowerShell или localhost не нужен. Новое `getFile()` необходимо при изменениях; сохранённый `File` не является живым потоком. [File System Access](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access).

Chrome поддерживает сохранение разрешений между посещениями с версии 122. Это уменьшает повторную настройку, но разрешение отзывное; сохранённый handle нужно проверять. [Persistent permissions](https://developer.chrome.com/blog/persistent-permissions-for-the-file-system-access-api).

Ограничения, которые должны решить судьбу прототипа:

- API picker прежде всего для Chromium; нельзя обещать одинаковую поддержку Firefox/Safari. Нужен feature detection и ручной режим.
- Выбор требуется от пользователя: сайт не может сам найти `%LOCALAPPDATA%` или получить произвольный доступ к диску.
- Browser может отклонить sensitive path; доступ к фактической папке Valorant надо проверить на Windows. Не просить весь AppData. [File System Access specification](https://wicg.github.io/file-system-access/).
- Фоновая вкладка может замедлять polling; нельзя обещать постоянную периодичность во время игры. [Chrome timer throttling](https://developer.chrome.com/blog/timer-throttling-in-chrome-88).
- Перезапись, truncate и замена файла при рестарте должны обрабатываться. File picker snapshot / `<input type=file>` не заменяет обновляемый handle.
- Без отдельного сигнала процесса возвращать «нет свежих данных», а не «игра закрыта».
- Точность карты/агента зависит от текущих логов. Наличие API чтения файлов не подтверждает наличие нужных game events.
- Лог обрабатывать локально; не отправлять весь файл на backend и не просить Riot lockfile/пароли.

**Вердикт:** разумный следующий PoC при жёстком требовании zero-install. Пригодность к production пока не подтверждена.

### Захват окна + OCR — технически возможен, UX сомнителен

`getDisplayMedia()` позволяет пользователю выбрать экран/окно, затем приложение может локально распознавать карту и агента. Разрешение нужно запрашивать при каждом новом вызове, через действие пользователя. Это не невидимый автоматический доступ. [Screen Capture specification](https://www.w3.org/TR/screen-capture/), [MDN getDisplayMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia).

Распознавание требует собственного PoC по языкам, разрешениям, full-screen, alt-tab и закрытию capture stream. Оно не доказывает состояние процесса; качество OCR для Valorant здесь не измерено. Для простого открытия справочника постоянный screen sharing выглядит более тяжёлой настройкой, чем ручной выбор. Не рекомендую как основной путь.

### Riot Account linking — для post-match функций

RSO требует production approval. Можно получать историю и результаты с backend, учитывая доступность данных и rate limits. Match history не следует выдавать за мгновенный сигнал завершения; опубликованный каталог не обещает latency SLA. `VAL-STATUS-V1` — состояние платформы, а не процесса конкретного игрока. [Riot docs](https://developer.riotgames.com/docs/valorant).

## Варианты с установкой

### Overwolf Electron + GEP

Перспективен при требовании полноценного lifecycle: событие игры, выбор агента, карта, начало/конец матча, собственный агент и другие поддерживаемые game events. Документация Valorant описывает scene/state, map и match ID. На странице есть ограничения отдельных режимов, например match_end для custom/training; нужен event snapshot при старте приложения в середине игры и проверка текущего provider status. [Valorant game events](https://dev.overwolf.com/ow-native/live-game-data-gep/supported-games/valorant/), [GEP overview](https://dev.overwolf.com/ow-electron/reference/Overwolf-electron-APIs/gep/Overview/).

Преимущество — события и обновления provider поддерживает отдельный поставщик. Это **не доказательство** более высокого uptime относительно нашего исправленного helper: сравнение на матчах ещё не проведено. Остаются зависимость от provider, согласование game enablement, изменения игры и native distribution.

Самостоятельное приложение может показывать тот же UI и получать game state внутри native runtime, убирая браузер → localhost из основного пути. Оно всё равно устанавливается; Electron также несёт более крупный runtime, чем узкий helper. Сроки, цена и коммерческие условия не оценены и требуют ответа поставщика.

### Собственный Windows helper

Для карты/своего агента может быть достаточно небольшого .NET/Rust приложения с понятной установкой, подписью, обновлением, uninstall и opt-in автозапуском. Подпись не гарантирует отсутствие всех SmartScreen/AV предупреждений. Ключевой выигрыш — исправленный detector и обслуживание, а не язык программирования.

Два независимых provider: process/lifecycle + logs; опционально внутренние Riot Client API после оценки доступности и допустимости. Внутренние pregame/core-game endpoint не имеют публичной гарантии совместимости и не должны быть единственной опорой. Пример первичной community-документации: [Riot client endpoints](https://valapidocs.techchrism.me/).

При сохранении сайта есть два транспорта: (а) pairing с localhost и нормальным LNA UX; (б) helper отправляет минимальное состояние по HTTPS в связанный аккаунт, сайт подписывается через backend. Второй устраняет браузерный доступ к localhost и работает на втором устройстве, но добавляет передачу данных, авторизацию, TTL, расходы и offline reconnect. Оба требуют установки helper. Это архитектурные предложения, не проверенные реализации.

PWA, расширение браузера или команда, которую нужно вставлять в PowerShell, не превращаются автоматически в zero-install process detector. PWA остаётся в browser sandbox; расширению для доступа к native процессам нужен соответствующий native компонент. Перенос требований с файла на copy-paste команду сохраняет настройку и поддержку.

## Как улучшить детект независимо от выбранного транспорта

1. **Единый контракт:** отдельно connection state, game state и freshness. Вместо перегруженного `timestamp` — `sessionId`, опциональный настоящий `matchId`, `observedAt`, `source`, `mapId`, `agentId`, `schemaVersion` и `helperVersion`. Unknown/stale не равны offline/lobby.
2. **Lifecycle:** остановка игры и смена аккаунта очищают состояние; неизвестный ответ API не завершает матч. Переходы agent-select → loading → match → ended обрабатываются явно.
3. **Parser:** incremental reading, сохранение контекста, обработка truncate/rotation, события в границах сессии. Мappings генерировать из общего каталога; неизвестную карту показывать без автоматического URL.
4. **Надёжный API provider:** deadlines, отмена, классификация not-in-match vs auth/rate-limit/network errors, refresh после рестарта клиента, backoff. Не подменять ошибку успешным lobby.
5. **Надёжная навигация:** один переход на сессию/матч; обновление агента в рамках той же сессии; явный opt-in auto-open; ручной выбор пользователя не перетирается каждым опросом.
6. **Recovery:** reconnect с полным snapshot, обновление при возврате вкладки, видимая дата последнего наблюдения; browser permission request отдельно от короткого HTTP timeout.
7. **Установка:** проверка версии и реального status payload, single-instance без убийства постороннего процесса, явное отключение автозапуска, обновление/uninstall, диагностические reason codes без токенов и полного лога.

Это предложения для следующего implementation этапа. В этом исследовании runtime-код не изменялся.

## Критерии следующего эксперимента

**Zero-install PoC:** Chrome и Edge на Windows; доступ к реальному логу; меню, очередь, выбор агента, матч, alt-tab, фон более 10 минут, конец, повторный матч на той же карте, restart Valorant/browser, revoked permission, rotation и отсутствие map event в новом хвосте. Проверять карту и собственного агента отдельно. Если карты до матча нет в логе, зафиксировать границу возможностей, а не угадывать.

**Native PoC:** все те же сценарии плюс late attach в середине матча, смена аккаунта/региона, dodge, reconnect, custom, deathmatch, training, provider unavailable, потеря интернета и обновление игры. Сверить native событие с наблюдаемым экраном; measure detection latency и ложные переходы. Точные обещания скорости и стабильности давать только после этих замеров.

Практический порядок: устранить доказанные contract/mapping/status дефекты → проверить browser log PoC → если его ограничения не подходят, native GEP PoC и сравнение с узким helper. Историю через RSO развивать отдельно, если она нужна продукту.

## Ограничения политики, относящиеся именно к этому продукту

Riot требует регистрации player-facing продуктов даже без официальных API. Политика также ограничивает performance-changing live подсказки и scouting. Автоматическое открытие пользовательского справочника по собственной карте/агенту не следует автоматически приравнивать ни к одобренному use case, ни к запрещённому overlay. Конкретный UX библиотеки lineups стоит описать при регистрации, особенно перед добавлением контекстных советов по раунду/позиции. Работа через Overwolf не означает автоматическое одобрение всех функций. [Riot policy](https://developer.riotgames.com/docs/valorant).
